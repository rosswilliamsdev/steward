## 1. Code Style & Formatting

### Python
- **Formatter:** Ruff (formatting + linting)
- **Line length:** 88 characters (Black-compatible default)
- **Indentation:** 4 spaces
- **Quote style:** Double quotes
- **Configuration:** Default Ruff settings

Run formatting:
```bash
ruff format .
```

Run linting:
```bash
ruff check .
```

### JavaScript/React
- **Formatter:** Prettier
- **Indentation:** 2 spaces
- **Semicolons:** Required (true)
- **Quote style:** Double quotes
- **Trailing commas:** All (ES5+)
- **Line length:** 80 characters
- **Configuration:** Default Prettier settings

Run formatting:
```bash
npx prettier --write .
```

### Enforcement
- Both tools should be run before committing
- Consider adding pre-commit hooks (e.g., `pre-commit` for Python, `husky` for JS)

## 2. Naming Conventions

### Python (Django)

- **Variables & functions:** `snake_case`
  ```python
  calculate_balance()
  user_name = "John"
  ```

- **Class names:** `PascalCase`
  ```python
  class Fund(models.Model):
  class DonorListView(ListView):
  ```

- **Constants:** `UPPER_SNAKE_CASE`
  ```python
  MAX_GRANT_AMOUNT = 100000
  DEFAULT_STATUS = "pending"
  ```

- **Django model fields:** `snake_case`
  ```python
  created_at = models.DateTimeField()
  nonprofit_name = models.CharField()
  ```

- **Database tables:** Auto-generated by Django (`appname_modelname`) unless overridden via `Meta.db_table`

- **Boolean fields:** Prefix with `is_` or `has_`
  ```python
  is_donor = models.BooleanField()
  is_admin = models.BooleanField()
  has_balance = models.BooleanField()
  ```

- **Private methods/variables:** Leading underscore
  ```python
  def _calculate_total(self):
  _internal_cache = {}
  ```

### JavaScript/React

- **Variables & functions:** `camelCase`
  ```javascript
  const calculateBalance = () => {};
  const userName = "John";
  ```

- **React components:** `PascalCase`
  ```javascript
  function DonorDashboard() {}
  const FundChart = () => {};
  ```

- **Constants:** `UPPER_SNAKE_CASE` for true constants
  ```javascript
  const API_BASE_URL = "/api";
  const MAX_RETRY_ATTEMPTS = 3;
  ```

- **Boolean variables:** Prefix with `is`, `has`, `should`, or `can`
  ```javascript
  const isLoading = true;
  const hasError = false;
  const shouldRender = true;
  ```

- **Event handlers:**
  - **Props passed down:** `on[Event]`
    ```javascript
    <button onClick={handleClick}>
    <form onSubmit={handleSubmit}>
    ```
  - **Handler functions:** `handle[Event]`
    ```javascript
    const handleClick = () => {};
    const handleSubmit = () => {};
    ```

- **Component files:** Match component name in `PascalCase.jsx`
  ```
  DonorDashboard.jsx
  FundChart.jsx
  ```

- **Utility/helper files:** `camelCase.js`
  ```
  formatCurrency.js
  apiClient.js
  ```

  - `test_views.py`
  - `test_forms.py`
  - `test_api.py`

- **Templates:** Follow Django convention: `funds/templates/funds/template_name.html`
- **Static files:** Follow Django convention: `funds/static/funds/css/`, `funds/static/funds/js/`

### React Frontend Organization

- **Location:** Separate `frontend/` directory at project root
- **Organization:** Type-based structure
  - `/components` — All React components
  - `/hooks` — Custom React hooks
  - `/utils` — Helper functions (e.g., `formatCurrency.js`)
  - `/api` — API client for communicating with Django REST Framework
- **Test files:** Colocated with components
  ```

  ```
- **Barrel files (`index.js`):** Minimal use
  - Main entry point only
  - Avoid elsewhere (can cause circular dependencies and slow bundling)

### Build Process

- React builds to `frontend/dist/`
- Django serves built bundles via `{% static %}` tags
- Django REST Framework provides API at `/api/` prefix

## 4. Component & Module Patterns

### Python (Django)

**Django Views (Class-Based Views):**
- Keep view logic minimal — delegate to models/managers
- Use mixins for reusable permissions/behavior
  ```python
  class FundListView(LoginRequiredMixin, UserPassesTestMixin, ListView):
  ```
- Method organization: follow Django's dispatch order
  - `get()`, `post()`
  - `get_context_data()`
  - `get_queryset()`
  - Helper methods last
- One view per class (avoid God classes)

**Business Logic:**
- **Model methods** for single-instance logic
  ```python
  @property
  def balance(self):
      return self.contributions.sum() - self.grants.sum()
  ```
- **Managers/QuerySets** for collection-level queries
  ```python
  class FundManager(models.Manager):
      def for_donor(self, user):
          return self.filter(donor=user)
  ```
- **Avoid service layers** for small projects — Django models are designed to hold business logic
- **Keep views thin, models fat**

**File Size Guidelines:**
- **Models:** Split into `models/` directory if >300 lines or >5 models
- **Views:** Split into `views/` directory by function (e.g., `donor_views.py`, `staff_views.py`) when >200 lines
- **General rule:** If scrolling feels tedious, split it

### JavaScript/React

**Exports:**
- **Prefer named exports** for components
  ```javascript
  export function DonorDashboard() {}
  ```
- Easier to refactor, better IDE support
- Default exports are falling out of favor in modern React

**Component Size:**
- **~150 lines or less** per component (including JSX)
- If a component has:
  - More than 3-4 pieces of state, or
  - 3+ `useEffect` hooks
  - → Consider splitting

**Shared Logic:**
- **Custom hooks** for stateful logic
  ```javascript
  function useFundData(fundId) {
    const [data, setData] = useState(null);
    // ... fetch logic
    return data;
  }
  ```
- **Utility functions** for pure logic
  ```javascript
  export function formatCurrency(amount) {
    return new Intl.NumberFormat('en-US', {
      style: 'currency',
      currency: 'USD'
    }).format(amount);
  }
  ```
- **Context** sparingly — only for truly global state (auth, theme)

**Component Patterns:**
- **Composition over props drilling** — pass children, not everything as props
- **Avoid container/presenter split** for small projects — unnecessary abstraction
- **Extract sub-components** when JSX gets nested >3 levels deep
- **Server state vs. UI state:**
  - For this project: `fetch` + `useState` is fine given small scope
  - Larger projects: React Query/SWR for server state

## 5. API & Data Layer Conventions

### Django REST Framework (Backend)

**Serializers:**
- Keep in separate `serializers.py` file
- One serializer per model as a starting point
  ```python
  class FundSerializer(serializers.ModelSerializer):
      class Meta:
          model = Fund
          fields = ['id', 'name', 'donor', 'balance']
  ```
- Use nested serializers sparingly (can cause N+1 query problems)

**ViewSets vs. APIViews:**
- **Use ViewSets** for standard CRUD operations
  ```python
  class FundViewSet(viewsets.ModelViewSet):
      queryset = Fund.objects.all()
      serializer_class = FundSerializer
  ```
- **Use APIViews** for custom endpoints that don't fit REST patterns
- For small projects: ViewSets are faster to scaffold

**API URL Structure:**
- Follow REST conventions:
  ```
  /api/funds/                    # List (GET), Create (POST)
  /api/funds/{id}/               # Retrieve (GET), Update (PUT/PATCH), Delete (DELETE)
  /api/contributions/
  /api/grant-recommendations/
  ```
- Use DRF's `DefaultRouter` for automatic URL generation
  ```python
  from rest_framework.routers import DefaultRouter

  router = DefaultRouter()
  router.register(r'funds', FundViewSet)
  ```

**Permissions:**
- Set default permission classes in `settings.py`
- Override per-viewset as needed
  ```python
  class FundViewSet(viewsets.ModelViewSet):
      permission_classes = [IsAuthenticated, IsDonorOrAdmin]
  ```

### React (Frontend)

**API Calls Location:**
- **Centralized `api/` directory** structure:
  ```
  frontend/src/api/
  ├── client.js          # Base fetch wrapper
  ├── funds.js           # Fund endpoints
  ├── contributions.js   # Contribution endpoints
  └── grants.js          # Grant endpoints
  ```

**API Client Pattern:**
- Create a thin wrapper around `fetch`:
  ```javascript
  // api/client.js
  const API_BASE_URL = "/api";

  export async function apiRequest(endpoint, options = {}) {
    const token = localStorage.getItem("authToken");

    const response = await fetch(`${API_BASE_URL}${endpoint}`, {
      ...options,
      headers: {
        "Content-Type": "application/json",
        ...(token && { Authorization: `Bearer ${token}` }),
        ...options.headers,
      },
    });

    if (!response.ok) {
      throw new Error(`API error: ${response.statusText}`);
    }

    return response.json();
  }
  ```

- Endpoint-specific functions:
  ```javascript
  // api/funds.js
  import { apiRequest } from "./client";

  export function getFunds() {
    return apiRequest("/funds/");
  }

  export function getFund(id) {
    return apiRequest(`/funds/${id}/`);
  }
  ```

**Error Handling:**
- **Try/catch in components** for this project size
  ```javascript
  const [error, setError] = useState(null);

  try {
    const data = await getFunds();
    setFunds(data);
  } catch (err) {
    setError(err.message);
    console.error("Failed to fetch funds:", err);
  }
  ```
- Display user-friendly error messages in UI
- For larger projects: consider error boundaries

**Loading States:**
- **Local state** pattern with `useState`:
  ```javascript
  const [isLoading, setIsLoading] = useState(false);
  const [error, setError] = useState(null);
  const [data, setData] = useState(null);

  useEffect(() => {
    async function fetchData() {
      setIsLoading(true);
      setError(null);
      try {
        const result = await getFunds();
        setData(result);
      } catch (err) {
        setError(err.message);
      } finally {
        setIsLoading(false);
      }
    }
    fetchData();
  }, []);
  ```

## 6. Testing Standards

### Django (Backend)

**Testing Framework:**
- Use Django's built-in `TestCase`
- Focus on unit tests for now; integration and e2e can be added later

**What Gets Tested:**
- **Authentication & authorization:** All permission checks, role-based access control
- **Security-critical paths:** Grant approval workflows, fund access restrictions
- **Business logic:** Model methods, properties (e.g., computed balance), managers
- Keep tests lean — cover critical paths, not every edge case

**Test Organization:**
```python
funds/tests/
├── test_models.py      # Model methods, properties, managers
├── test_views.py       # View permissions, access control
├── test_forms.py       # Form validation
└── test_api.py         # DRF endpoints, serializers
```

**Example Test:**
```python
from django.test import TestCase
from funds.models import Fund, User

class FundPermissionTests(TestCase):
    def setUp(self):
        self.donor = User.objects.create_user(
            username='donor1',
            is_donor=True
        )
        self.fund = Fund.objects.create(
            name='Test Fund',
            donor=self.donor
        )

    def test_donor_can_only_view_own_funds(self):
        # Test that donors can't access other donors' funds
        pass
```

**Running Tests:**
```bash
python manage.py test
```

### React (Frontend)

**Testing Framework:**
- **Vitest** for unit tests

**What Gets Tested:**
- **Utility functions** only (e.g., `formatCurrency`, `calculateTotal`)
- Keep it lean — skip testing UI components for now

**Test Organization:**
```
frontend/src/utils/
├── formatCurrency.js
└── formatCurrency.test.js
```

**Example Test:**
```javascript
import { describe, it, expect } from 'vitest';
import { formatCurrency } from './formatCurrency';

describe('formatCurrency', () => {
  it('formats USD amounts correctly', () => {
    expect(formatCurrency(1000)).toBe('$1,000.00');
  });
});
```

**Running Tests:**
```bash
npm test
```

### Testing Philosophy

- **Lean approach:** Test what matters (auth, security, critical business logic)
- **No coverage targets:** Focus on meaningful tests, not hitting a percentage
- **Start small:** Unit tests first; add integration/e2e as the project scales
- **Colocate tests:** Keep test files next to the code they test (frontend) or in organized `tests/` directory (Django)

## 8. Error Handling

### Django Views
- Use `try/except` blocks for operations that can fail
- Display user-friendly error messages via Django messages framework
- Log errors for debugging

```python
from django.contrib import messages

def approve_grant(request, pk):
    try:
        grant = GrantRecommendation.objects.get(pk=pk)
        grant.status = 'approved'
        grant.save()
        messages.success(request, 'Grant approved successfully.')
    except GrantRecommendation.DoesNotExist:
        messages.error(request, 'Grant not found.')
    except Exception as e:
        messages.error(request, 'An error occurred. Please try again.')
        logger.error(f"Error approving grant {pk}: {e}")

    return redirect('grant_list')
```

### Django REST Framework APIs
- Let DRF handle standard errors (400, 404, etc.)
- Return appropriate HTTP status codes
- Use consistent error response format

```python
from rest_framework.response import Response
from rest_framework import status

def create(self, request):
    try:
        # ... validation and creation logic
        return Response(serializer.data, status=status.HTTP_201_CREATED)
    except ValidationError as e:
        return Response({'error': str(e)}, status=status.HTTP_400_BAD_REQUEST)
```

### React Components
- Use `try/catch` in async functions
- Store error state and display to user
- Log errors to console for debugging

```javascript
const [error, setError] = useState(null);

try {
    const data = await getFunds();
    setFunds(data);
} catch (err) {
    setError(err.message);
    console.error("Failed to fetch funds:", err);
}

// In JSX:
{error && <div className="error">{error}</div>}
```

### General Principles
- **User-facing errors:** Simple, actionable messages ("Grant not found" not "DoesNotExist exception")
- **Developer errors:** Log full stack traces for debugging
- **Consistency:** Use the same error patterns throughout each layer (Django views, DRF APIs, React)

## 9. Environment & Config

### Django

**Environment Variables:**
- Use `python-decouple` or `django-environ` to manage environment variables
- Store sensitive configuration in `.env` file (gitignored)
- Never commit secrets (`SECRET_KEY`, database credentials, API keys)

**Setup:**
```bash
pip install python-decouple
```

**settings.py:**
```python
from decouple import config

SECRET_KEY = config('SECRET_KEY')
DEBUG = config('DEBUG', default=False, cast=bool)
ALLOWED_HOSTS = config('ALLOWED_HOSTS', default='localhost').split(',')

DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.postgresql',
        'NAME': config('DB_NAME'),
        'USER': config('DB_USER'),
        'PASSWORD': config('DB_PASSWORD'),
        'HOST': config('DB_HOST', default='localhost'),
        'PORT': config('DB_PORT', default='5432'),
    }
}
```

### React (Vite)

**Environment Variables:**
- Prefix all variables with `VITE_` to expose them to the client
- Store in `.env` file (gitignored)
- Access via `import.meta.env.VITE_VARIABLE_NAME`

**.env:**
```bash
VITE_API_URL=http://localhost:8000/api
```

**Usage in code:**
```javascript
const API_BASE_URL = import.meta.env.VITE_API_URL || "/api";
```

### File Structure

**`.env`** (gitignored):
- Contains actual values for local development
- Each developer has their own copy
- Never committed to version control

**`.env.example`** (committed to repo):
- Template showing all required environment variables
- Contains placeholder values (no secrets)
- Developers copy this to `.env` and fill in real values

**Example `.env.example`:**
```bash
# Django
SECRET_KEY=your-secret-key-here
DEBUG=True
DB_NAME=steward_db
DB_USER=postgres
DB_PASSWORD=your-password
DB_HOST=localhost
DB_PORT=5432

# React
VITE_API_URL=http://localhost:8000/api
```

### .gitignore

Ensure these files are gitignored:
```
.env
.env.local
.env.*.local
```
